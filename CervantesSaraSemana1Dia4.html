# Contexto para Agentes de IA - Control de Asistencia ## Proyecto Sistema web para registrar, consultar, editar y eliminar asistencia de aprendices por fecha (SENA), con autenticación exclusiva de instructores. ## Stack - Python 3.10+, Flask 3.x, SQLite3, Jinja2, python-dotenv. - Testing y Calidad: Pytest, Ruff, Pre-commit. ## Comandos - Entorno: `python -m venv .venv && source .venv/bin/activate` (o `.venv\Scripts\activate`) - Instalar dependencias: `pip install -r requirements.txt` - Ejecutar: `python app/main.py` - Pruebas: `pytest tests/` - Linter: `ruff check .` / Formato: `ruff format .` ## Estructura - `app/`: Lógica de la aplicación y base de datos (`main.py`). - `templates/`: Plantillas HTML (`base.html`, `login.html`, `asistencia.html`). - `tests/`: Pruebas de humo (`test_humo.py`) y pruebas de regresión (`test_fallos.py`). - Archivos raíz: `.env.example`, `.gitignore`, `pyproject.toml`, `requirements.txt`. ## Qué no hacer - NUNCA quemar secretos, tokens o contraseñas en el código fuente. - NO subir `.env`, bases de datos SQLite (`*.db`) ni `.venv` a Git. - NO omitir validaciones de sesión en endpoints de modificación o eliminación. - NO almacenar contraseñas en texto plano; usar siempre hashing seguro. ## Lecciones aprendidas - Todo endpoint que mute o elimine datos debe verificar la sesión activa del instructor antes de tocar la BD. - Las contraseñas nunca deben guardarse ni validarse en texto plano; usar hashing robusto (Werkzeug). - Validar en el backend con listas blancas estrictas y no confiar únicamente en los formularios HTML.

### Qué cambia - Se extraen claves criptográficas y secretos a variables de entorno con `python-dotenv` y `.env.example`. - Se implementa red de seguridad con Ruff linter, Pytest y configuración de pre-commit hooks. - Fallo 1 corregido: Control de acceso en la ruta `/asistencia/eliminar/<id>` exigiendo sesión activa. - Fallo 2 corregido: Hashing seguro de contraseñas de instructor con `werkzeug.security` (scrypt/pbkdf2). - Fallo 3 corregido: Validación estricta en servidor con lista blanca para estados de asistencia. ### Por qué se hizo así - Para mitigar riesgos críticos de OWASP (A01 Broken Access Control, A02 Cryptographic Failures, A07 Identification Failures). - Se aplicó metodología TDD (ciclo Rojo/Verde) garantizando que cada corrección cuente con prueba automatizada de regresión. ### Qué podría romperse - Clientes que intentaban eliminar registros sin cookie de sesión activa ahora recibirán redirección HTTP 302 hacia `/login`. - Registros directos con estados distintos a 'Presente', 'Ausente' o 'Excusa' serán rechazados por el backend.
